# Portal application workspace

`mountApplication(context)` in `core/account/portal/application.ts` is the application lane of the authenticated portal. The central shell creates, restores and signs out the account, then mounts this view with its `PortalContext` ([types](../core/account/portal/types.ts)). The view adds no store, timer history or auth of its own. It reads and writes only through `context.client.request` on the existing `/preparation` and `/google/list` APIs, so cookie, CSRF, origin and account namespace stay authoritative.

## What the user sees

- **Tasks**: this account's retained preparation tasks (`/preparation/list`), with state and revision. Empty, unconfigured (`PREPARATION_NOT_CONFIGURED`) and load-failure states are stated as such.
- **Review**: the selected task's current revision (`/preparation/status`): request, state, blocker, next action, checklist, prepared answers with *needs input* / *corrected by you* flags, and correction history from the server's visible session record.
- **Sources and files**: citation buttons and source snapshots open in the side panel. PNG/JPEG/WebP files preview inline. PDFs open in a new tab. Text/OCR/JSON records show as inert text. Every file is fetched through `/preparation/artifact`, checked against the SHA-256 recorded by the server, and offered as an exact download. The Blob URL is revoked when it is replaced, the selection changes or the view unmounts. Current and earlier-revision files are separated using the backend's `current` binding check, never inferred by the browser.
- **Corrections**: *Save correction* calls `/preparation/correct` with the displayed `expectedRevision`. The view says that regenerated documents and photos come from the backend. Earlier files stay listed as earlier revisions; the view never presents an overlay as a regenerated PDF or photo. A `STALE_PREPARATION_REVISION` reply reloads the current revision, keeps the user's unsaved text visible and saves nothing. While the server is paused, a task is working or a task is cancelled, corrections are held.
- **New application**: offered only when a connected Google account has a saved folder and processing is not paused. Processing consent is an explicit checkbox showing the configured cost limit. Drive saving is a separate opt-in. Each exact intent keeps one request ID, so a user retry after an unknown outcome is idempotent. Nothing retries automatically.
- **Approve and submit**: *Check destination (read-only)* calls `/preparation/browser-review` with the current revision and no mapping. It shows the destination, submit and receipt URLs, the review fingerprint, every value with its label, correction flag and citation count, the submission identity Spindle sets, and each current file with its full SHA-256 and a preview. The mapping is server-owned, see [owner-approved browser submission](PREPARATION_BROWSER_APPROVAL.md). *Approve and submit this exact review* is enabled only when `/preparation/config` reports `browserApproval.available`, a review for the current revision is displayed, and no submission exists. It sends exactly `{taskId, expectedRevision, fingerprint, requestId}`; one request ID per displayed review makes a retry a replay. While the run works, *Stop* routes to `/preparation/cancel`. A retained submission shows its receipt or an unknown outcome. *Check receipt (read-only)* calls `/preparation/browser-reconcile` and never resubmits. Without the operator gate, the button is labelled unavailable and nothing can be submitted.

Live status polls every 1.5 s only while execution is `running` or `queued`. A failed poll stops and asks the user to press Refresh. Aborting the context, or the account changing, stops polling, removes listeners, revokes Blob URLs, empties the root and drops late replies. Sign-in failures (`SIGNIN_REQUIRED`, 401, `CSRF_DENIED`, `ACCOUNT_CHANGED`) go to `context.onError` so the shell decides. Other failures show fixed messages for protocol codes; arbitrary backend text is never echoed as an error. All backend values are rendered with `textContent`; Drive links must be `https:` and verified.

Selectors and classes are prefixed `application-` / `data-application-*`. Shared vocabulary is limited to `.portal-card`, `.portal-grid`, `.portal-actions`, `.portal-muted`, `.portal-error`, `.portal-status` and `.portal-badge`; the shell owns CSS.

## Checks

- `node --max-old-space-size=256 --test --test-concurrency=1 build/tests/account/portal-application.test.js` (included in `npm test` / `make check`). It runs a real account server, client, AgentStore and EvidenceStore with an **invented stored task** and a **minimal fixture DOM**, not a browser. It covers list → review → citation/photo/PDF previews with hash checks → Blob revocation → remount persistence, stale-revision conflict, paused holds, read-only destination check, empty/other-account/unconfigured states, and sign-in hand-off. It also checks that a late reply after abort does not paint. No Google, model or execution call is allowed. With a fixture continuation it also checks that the configured review shows the exact values and current hashes and never the earlier PDF. It checks that approve sends only the displayed fingerprint, revision and request ID, that a retry reuses that ID, and that a retained uncertain submission offers only the read-only receipt check.
- `tests/account/portal-application.e2e.ts` is the ~45 s Chromium journey and recording script, run only when the coordinator schedules Chromium (usage in the file header). It signs in through the existing `/connections` form (HttpOnly cookie + CSRF) and exercises the real `/preparation` API. It also verifies the downloaded PDF bytes against the stored SHA-256, reloads and checks persistence, and records a cross-device conflict. The script predates the served portal shell and uses static harness scripts only; the script asserts that no backend request was intercepted. The task data is an invented fixture, and the recording is labelled as such.

## Open gaps and backend requests

- A correction that succeeds against a live Google-bound task, and regeneration of its outputs, needs a Google-bound task. That pilot is selected separately within the existing budget; the tests cover only the conflict and paused paths through the real API.
- **Approval/execution/receipt** exists only for the developer-fictional destination behind the operator gate. Its activation conditions are listed in [PREPARATION_BROWSER_APPROVAL.md](PREPARATION_BROWSER_APPROVAL.md).
- **Task timestamps**: `/preparation/list` returns no created/updated time, so the list cannot sort or say "updated 2 min ago".
- Native/Mac acceptance does not apply. This lane is a browser view over account APIs and captures nothing.
