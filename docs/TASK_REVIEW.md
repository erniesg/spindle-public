# Task preparation preview

This partial #49 component shows real persisted AgentStore tasks and their current checklist. It does not yet connect application fields, source viewers, corrections, attachments or submission. Those requirements remain pending on #48/#50; this is not an alternative application model or completed connected-agent demo.

`startTaskReview(store, {workspaceId, accountId})` explicitly starts a numeric-loopback HTTP server. The trusted caller selects the namespace, not the model or URL. Open its returned local URL privately: the random bearer fragment moves into tab session storage and is removed from browser history before rendering. Do not put that URL in evidence. Closing the tab does not stop an independently running AgentRuntime. Closing the server stops web delivery, not a worker supplied separately by the caller. No capture, browser enrollment, OS notifications, startup registration or telemetry starts here.

SQLite triggers create a preparation notice in the same transaction as admission/status transition. Repeated admission and same-status updates do not produce duplicate notices. Rollback rolls back notices. Existing tasks receive no invented historical events when the feature is installed. Notices contain a constant status message and task deep link, not document/account values. The web page acknowledges a notice only after a paint opportunity while it intersects the visible viewport. An acknowledgement is durable; reopening does not requeue acknowledged notices. This is web delivery, not proof a human read it. A closed tab queues notices until reopening; there is no closed-window OS delivery claim. Submitted notices await verified receipt integration.

Task `ready` means **Preparation needs review**, never a validated application or submitted result. The main page states the missing application connection prominently. It presents milestone states and next action without percentages or claimed verified counts. Technical Task payloads remain in a closed disclosure; all text is inert. Polling keeps task links and the disclosure mounted so keyboard focus and expansion survive updates. A delayed task response cannot overwrite a newer task selection.

Build with `npm run build`, then explicitly run `node build/core/assistant/main.js /private/path/agent.sqlite WORKSPACE ACCOUNT` for an existing worker database and its trusted namespace. The terminal prints the private local link; never capture that terminal in media. Stop with Ctrl-C. This preview command does not create tasks or start a worker. Both `npm test` and `make check` already include `tests/assistant/*.test.ts` through their shared `build/tests/*/*.test.js` glob. The browser journey is separate: `node build/tests/assistant/task-review.e2e.js` with `SPINDLE_REVIEW_CHROMIUM` set to an existing clean Chromium executable and `SPINDLE_TASK_REVIEW_OUTPUT` to a private ignored directory. Its scripted provider is a fixture; SQLite, AgentRuntime, HTTP and Chromium are real. It does not establish live Gmail/model/native or complete application acceptance.

## Automatic shared user memory

The optional fourth `startTaskReview` argument enables **Tell Spindle**, separate from the manual local task context below. It accepts typed turns and automatically learns through the existing configured AgentProvider/runtime when conversation learning and model processing are enabled; sync is an independent opt-in. See [the service/CLI integration contract and proof limits](USER_MEMORY.md). No provider configured means queued turns with a visible configuration blocker, never pretend inference. Credentials stay in the existing account client, not either memory store. Existing two/three-argument callers keep working.

## Saved user context alpha

Optionally pass the existing `EvidenceStore` as a third argument: `startTaskReview(store, namespace, evidence)`. The two-argument API still works without memory storage. The CLI accepts an optional fourth `CONTEXT_DIRECTORY` argument, explicitly opening/creating the existing EvidenceStore layout there; omitting it creates no context directory. Use the same directory as the worker's `contextTools` binding to share saved context. The caller owns both stores and closes them after the server/worker stop.

The small saved-context panel lists facts, preferences and goals, lets the user add or correct them, and shows origin, revision history and source IDs. It is separate from task polling so unsaved edits survive updates. Source IDs are provenance identifiers, not exact-source viewer links. The trusted startup namespace fixes account/workspace for every request. Authenticated `GET /api/memory?after=KEY` returns up to 50 effective records in key order; `GET /api/memory/history?key=KEY&before=VERSION` returns up to 100 older revisions, ascending. The panel pages both. Authenticated `POST /api/memory` accepts only `{key, kind, value}`, requires the exact local Origin and JSON content type, and rejects bodies over 32 KiB. User writes always set correction authority; model tools cannot set it. Earlier inferred source IDs remain in history. There is no forget/delete action in this alpha.

Saved context is about the user, not current source evidence or permission to use AI, prepare or submit. No automatic ingestion, remote processing or capture is added. Use invented context only on development hosts. The data is private plaintext SQLite in the supplied EvidenceStore, not encrypted. The browser check `node build/tests/assistant/memory.e2e.js` uses `SPINDLE_REVIEW_CHROMIUM` and optional `SPINDLE_MEMORY_REVIEW_OUTPUT`; it exercises real UI/HTTP/SQLite with invented content, not a live model. `tests/assistant/memory.test.ts` separately closes/reopens both stores after HTTP entry and verifies the registered tool result is observed by a scripted provider through AgentRuntime.

Local task data and notification metadata use the existing private plaintext agent database. The trusted caller owns file permissions and retention; there is no encryption claim. Stop the explicitly owned server and worker before removing their test database. No dependency or lockfile changes are required.
