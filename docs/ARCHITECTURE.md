# Desktop capture systems design

Status: target boundaries for the rebuild, with the implemented Capture Check subset described below; not a claim that full collectors exist. [PRODUCT.md](PRODUCT.md) owns the product; this document owns module responsibilities and data flow. [TESTING.md](TESTING.md) owns shared validation gates. ## Desktop capture milestone

This page's ownership and data-flow rules describe desktop capture, not the whole product or prerequisites for every feature. The separately [accepted connected-agent milestone](PRODUCT.md#accepted-connected-agent-milestone) uses explicitly selected Google sources and preparation/AI authority; it need not wait for native capture acceptance. Nothing here authorizes routing captured personal activity into that connected experience.

Deliver inspectable, correctly timed local capture on Windows and macOS, each in Default and Rich mode. `default` is the canonical engineering profile name; “Basic” in product discussions means the same profile. Rich adds visuals to the same visits, not a second recorder. The collectors themselves do not require a classifier or live network. The separately accepted [account-linked tracker milestone](PRODUCT.md#accepted-account-linked-tracking-milestone) requires one account/shared history (#66) and labelled session review (#67); fully local/account-free delivery is deferred. Do not turn the collector boundary into a product gate against that milestone.

Supported OS versions, architectures, native toolchains, packaging and IPC are decisions in the foundation issue, with a small target-device spike before production integration. Start with one supported version/architecture per OS; do not imply universal desktop support. Python 3.11+ is currently a **development-check dependency only**, not a selected product runtime. Candidate native APIs are Windows foreground/WinEvent + UI Automation + Windows.Graphics.Capture/Windows.Media.Ocr, and macOS NSWorkspace/Accessibility + ScreenCaptureKit/Vision. Validate API availability, permissions and capture scope; these are candidates, not proven implementations.

## Current review implementation: Capture Check

`core/capture-check/` contains a strict TypeScript Node 22 inspector/state engine with no runtime npm dependencies. `npm ci --ignore-scripts` installs pinned development tooling; `npm run typecheck` checks types and `npm run build` recreates ignored `build/` JavaScript and browser assets. Source and package launchers execute `build/core/capture-check/app.js`; package building regenerates outputs before fingerprinting source and generated files. User ZIPs contain no compiler or `node_modules`. Tests and optional browser journeys are also strict TypeScript, compiled beside the runtime under `build/`; they execute generated entry points. Pinned development-only `playwright-core` provides actual browser API types and the optional browser driver, without automatic browser downloads. The protocol types in `types.ts` describe only the fixture probe, not the draft production contract. It owns bounded in-memory visits/readback, recording epochs, stale-result rejection and a constructor-based content-free feedback export. Its HTTP interface binds only to numeric loopback on an ephemeral port; data/control routes require a random bearer token, strict Host/Origin checks and bounded bodies. There is no HTTP capture-ingest endpoint, telemetry or remote transport. UI text is rendered inertly, not interpreted as HTML.

`platforms/macos/CaptureCheck.swift` uses NSWorkspace/AXObserver plus a 50 ms focus fallback and bounded 250 ms static-text reads. `platforms/windows/CaptureCheck.cs` uses WinEvent plus the same fallback and background UI Automation reads. Both preserve observed transitions separately from slower text. Capture accepts only parent-selected fixture PIDs **and** verifies the frontmost process is the same executable as the fixture-capable reader; feeding an arbitrary browser PID to the helper cannot enable browser capture. The fixture is a separate native process, not a producer of captured text; its A/B activation messages are an independent diagnostic trace only.

Windows additionally checks observation continuity before sampling the current foreground window. More than one second without observation, or an in-run WinEvent notification over one second old (using wrapping TickCount timestamps), stops the reader and emits an epoch-bound `coverageGap` at the earlier of its last observation and the delayed source event. The stop-command path also checks continuity, so a queued stop cannot hide a stall by running before the timer. The shared controller cancels scheduled switches, truncates visits and removes samples at/after that cutoff (even if the controller already paused), rejects late text, preserves `WINDOWS_COVERAGE_GAP` in feedback, and permits a new test. This conservative preview watchdog reports lost coverage; it does not reconstruct missed visits or establish an accepted timing/coverage budget. Mac uses the same one-second observation-silence safety ceiling before AX work and on queued Stop, reporting `MAC_COVERAGE_GAP` through the same epoch-bound invalidation path. AX notifications lack source timestamps, so this does not detect every delayed notification with otherwise live polling. Native fault verification is separate from the deterministic guard/controller tests.

This subset has no pixels/OCR, browser extension, idle/attention accounting, disk context retention, encryption, startup install or long-term history. Bounded local memory readback of invented static text is a native API smoke test, not Default acceptance or proof of arbitrarily short-visit retrieval. Full encrypted retention and continuous frame providers below remain target design.

Windows review packages include a cross-compiled AnyCPU .NET Framework 4.8 executable (4.8.1 runtime on ARM), built without PDBs; no PowerShell script/policy bypass or SDK is required on the test host. Capture Check Mac packages compile their bundled Swift reader on the recipient Mac and require Command Line Tools. The separate integrated Preview package uses a precompiled Swift helper and bundled Node; its recipient launch does not require CLT, an SDK or a source checkout. Structural validation is not build attestation or installed acceptance; Gatekeeper/notarization and permission-preserving upgrades remain unproven. See [Mac producer and package checks](MAC_PREVIEW_NATIVE_BUILD.md). Node is bundled from checksum-pinned official archives, with upstream licence notices, on both OSes. This deliberately avoids introducing Rust/FFI dependencies for the first native text probe; it does not choose the final pixel-capture provider.

`tools/package_capture_check.py` builds source-bound review ZIPs/checksums from a clean commit; it does not deploy or run native acceptance. See [TRY_CAPTURE.md](TRY_CAPTURE.md) for the human handoff. Native runs and Mac compilation still require review on the target machines.

## Integrated capture PREVIEW

`core/preview/` is the new preview integration owner for both native adapters, controls and AES-GCM retained readback; [contracts/preview](../contracts/preview/README.md) versions the integration separately from the unfinished production freeze. `platforms/macos/Preview.swift` joins AX, a ScreenCaptureKit/Vision worker adapted from #21 and Keychain; `platforms/windows/Preview.cs` joins foreground/UIA, exact-HWND Windows.Graphics.Capture/Windows.Media.Ocr and current-user DPAPI. Browser detail uses explicit Chrome extension registration, deliberate profile pairing, encrypted persistent enrollment and authenticated bounded local IPC, never native browser fallback. [Candidate scope/instructions](CAPTURE_PREVIEW.md) distinguish source, cross-build, synthetic and unrun native proof. Authorized native window pixels are independent of optional AX/UIA text extraction and read-only/edit-state/layout policy, per the [owner correction](https://github.com/erniesg/spindle/pull/33#issuecomment-6385078156). Supported families remain provenance-verified Mac system Preview/Finder, Windows live OS-package/Store-or-System-signed Photos and exact OS-path Explorer/Notepad/Paint, plus run-owned fixtures. Explicit source allowlisting and pixel consent remain required; this is not all-app/name-only admission. Edited content, sheets and unfamiliar image layouts within an admitted native window are not pixel blockers. Window OCR/screenshots include visible content and chrome, including edited or sensitive fields; no masking or image-only crop is claimed. Structured text still skips password/editable/unknown subtrees, with incomplete text an OCR hint rather than pixel admission. Optional sensitive-content/read-only policy is tracked in [separate issue #34](https://github.com/erniesg/spindle/issues/34), not compiled, auto-enabled or a capture acceptance gate. These are unrun new-head native candidates, not universal app coverage. Windows uses a bounded persistent exact-HWND Windows.Graphics.Capture stream; this does not establish universal compositor or rapid-visit coverage; Mac uses generation/worker/host-PTS-fenced persistent ScreenCaptureKit. It associates the focused AX window by process and geometry; colliding bounds additionally require a unique exact nonempty title match in ScreenCaptureKit and fresh CoreGraphics metadata. Missing or duplicate titles at identical bounds remain unavailable; front-to-back order is not treated as keyboard focus. Slow Mac AX scanning is off the timing thread; both providers revalidate each acquisition/processing stage and terminate a stuck worker after a 3-second safety ceiling even when paused. Mac Accessibility and Screen Recording grant/required states are exposed separately; acquisition/association failures have content-free statuses. Browser Rich supports explicit manual capture and separately enabled automatic screenshots on enrolled, allowed ordinary origins, including editing pages; structured extraction still excludes editable/form values. Pixel consent does not grant universal website, private or embedded-document support. The old Capture Check is preserved as its fixture-only baseline, not a second platform production ledger. No draft Python checker is imported into runtime.

## Account-linked tracker integration

The [product milestone](PRODUCT.md#accepted-account-linked-tracking-milestone) owns the four-delivery scope. #66 owns authenticated account/device association, durable shared history and bounded offline/retry sync, consuming capture identities/history from #2/#3/#7. #67 owns the tracker session/range projection, non-double-counting device overlaps and labelled review UI, consuming #23/#24. Neither is the connected-agent task/evidence database or its application-review UI (#49).

The current `core/tracking/` implementation connects the existing native/browser visit owner through the shared history sink, with encrypted durable pending state, account/device history, session projection and persistent labels/corrections. See [TRACKING_API.md](TRACKING_API.md) for the account-only viewer and device-bound producer contracts, optional canonical HTTPS proxy origin, run instructions and explicit native/#67 gaps. Local API/browser proofs do not establish supported-host execution, installed acceptance or a deployed service.

One owner changes the shared history/types seam; Mac/Windows collectors and browser integration consume it. Preserve original device/recording/visit and clock provenance, source scope, deletion revisions and exact screenshot associations. Account sign-in does not start capture. Consent to record, retain/sync or send to a remote model remains distinct. Local pending data survives offline/restart and sync cannot resurrect a deletion.

Normal product setup automatically creates/retrieves OS-protected secrets and persists deliberate choices/trusted enrollment; users must not create Keychain entries or re-pair on every routine restart. Rich is selected by default only subject to explicit recording/pixel/retention consent. Stable packaging identity and supported OS behaviour still need actual tests. The implementation restores encrypted choices/enrollment and retrieves its OS-protected key on launch, always paused. The existing preview's account setup now saves service/account/device hints in that same protected settings vault, reopens the existing encrypted collector client/queue without device reenrollment, and exposes explicit upload/sync controls. Timer service origin is saved there too when settings are ready; timer signin/grants remain run-local. This setup is not the separately owned shared-history dashboard. This source wiring is not certification of supported-host key access, native enrollment or installed behavior.

The preview serializes account/settings ownership across key recovery, signin, sync, inspection, erasure and browser revocation. Key changes, lock and terminal Quit synchronously disable readiness and detach collector admissions; replacement waits for admitted work, including unpublished reopen inspection writes, to drain. Recovery failure stays unavailable until an explicit successful key recovery; it never adopts another account, discards the encrypted queue or starts recording. Timer signin/settings publication uses that same admission boundary; timer-only controls remain separate. These are shared lifecycle guarantees, not native OS-key acceptance.

The immediate shared-history implementation may use an authenticated account-backed server with TLS outside loopback and appropriate encryption/access controls at rest; declare which runtime can decrypt it. Fully local sync, elaborate pairing and E2EE recovery are not prerequisites, and no E2EE is claimed. This design authorises no new hosting, deployment or personal-data transfer to the development VM. Test with invented data and verify account isolation. Device-time reconciliation is a projection over captured observations, never a second capture clock or inferred attention score.

## Data flow and trust boundaries

```text
native foreground events ─────────────┐
enrolled browser transitions ─────────┤
                                     ▼
                       visit owner + monotonic timing
                                     │
                 pre-read permission/exclusion/privacy gate
                                     │
             optional native text / DOM / OCR / image workers
                                     │
                    revalidate visit + consent + deletion
                                     ▼
                     atomic local ingest / bounded queue
                         │                     │
                  observation ledger      encrypted context store
                         └──────────┬──────────┘
                             local inspect/delete UI
```

The diagram is logical: exclusion checks also run before sensitive reads in each producer, not only after central ingestion. A queue or diagnostic is a data sink too. Late processing must not move a visit boundary, extend its duration or bind old content to the next foreground target.

### Visits and time

- Record source event time before slow identity/text work. Preserve wall-clock instants plus monotonic elapsed information; clock rollback cannot create work.
- Bind every optional result to recording session, source/profile, visit/document identity, native process/window incarnation where applicable, and consent/deletion revisions. Timestamps alone are insufficient.
- A → B → A creates distinct visits even if content is identical. SPA navigation/reload, focus changes, lock, idle and restart have explicit lifecycle rules.
- Foreground app and matching browser detail describe one observed interval, not two. Per-device evidence remains separate from future cross-device person-time reconciliation. The single-device collector alone does not provide a combined-device summary; #67 owns that report in the account-linked tracker milestone.
- Unknown focus, missing heartbeat, permission loss and sleep create explicit partial/gap states. Basic app capture may continue when optional context is unavailable; private-browser detail cannot fall back to native title/OCR.

### Continuous capture and rapid changes

The user-facing requirement is to retrieve the permitted content seen in the active window, including short visits and content changes within the same window/tab. A periodic screenshot or one delayed read after a switch is insufficient. This does not justify promising that every rendered frame is recoverable: permissions, protected surfaces, rendering, stream delivery and overload impose measurable limits. Report gaps rather than returning a stale image/text as if current.

Use separate lightweight context timing and expensive extraction paths:

1. Record app/window/tab/document transitions immediately using native/browser events; never debounce away a visit because OCR or a settling timer is running.
2. Keep permitted native capture sessions alive where appropriate instead of launching a one-shot screen-capture process for every sample. Reconfigure target filters with explicit generation fences; switching capture targets may create a gap that must be measured.
3. Receive timestamped frames into a bounded, ephemeral in-memory buffer. Match a frame's source identity, capture timestamp and stream generation to the verified visit—not the window focused when OCR finishes. Never select an arbitrary old “latest frame” for a new visit. A browser window ID alone does not identify the tab/document inside it.
4. Refresh permitted text on relevant AX/UIA/DOM content-change events and on a bounded fallback heartbeat, even without focus changes. Never log keystrokes or read structured form-entry values; separately consented native window pixels can include visible edited fields. Coalesce redundant extraction, not context boundaries; prioritize a representative frame for each short visit over repeatedly processing the long current visit.
5. Extract native/DOM text first and OCR admitted frames locally. Release temporary pixels under Default; Rich retains only separately authorized images. Mark dropped/stale/unmatched coverage explicitly and clear buffers on pause/revoke/exclusion/lock/delete.

Continuous **acquisition**, text extraction cadence and retained-image cadence are different budgets. Do not OCR/encode/copy every compositor frame merely because the API delivers one. Conversely, a one-frame “latest only” cache plus slow OCR cannot prove short-visit retrieval. Measure the bounded buffer/queue policy against native rapid-switch and same-tab content-change oracles before selecting rates or claiming coverage. No unfiltered monitor recording or always-retained video is introduced by this design.

### Learn from Screenpipe; improve the existing collectors

Owner clarification, 25 October 2026: Screenpipe is an **engineering reference, not a proposed code dependency or rewrite**. Learn from the [current event-driven capture](https://github.com/screenpipe/screenpipe/blob/5d84243ab130270c951543846f87fdec367cf19a/crates/screenpipe-engine/src/event_driven_capture.rs) and [persistent WGC/readback design](https://github.com/screenpipe/screenpipe/blob/5d84243ab130270c951543846f87fdec367cf19a/crates/screenpipe-screen/src/wgc_capture.rs). The account-linked tracker should apply useful principles to its existing native/browser seams:

- Preserve observed activity transitions/time independently of screenshot, OCR and storage latency. Coalesce expensive enrichment, not visits.
- Trigger enrichment on meaningful context/content changes with a bounded periodic refresh; avoid repeating OCR/encoding when evidence is unchanged. Identical accessibility text does not prove identical pixels.
- Separate persistent acquisition from expensive frame readback/processing; do not OCR or CPU-copy every compositor frame merely because it arrives.
- Bound queues, memory and optional work so slow extraction cannot stall tracking. Retain source/time/generation fences, invalidate stale frames on target/permission/lifecycle changes, and never relabel a cached frame as a new visit.
- Expose missing/stale/dropped Rich coverage honestly. Automatic Rich remains required for the requested tracker, but perfect OCR or a screenshot for every arbitrarily short visit is not an added prerequisite; missing enrichment must not erase valid activity timing.

Use the existing #4/#5/#6/#8/#9 and #66/#67 work and affected invented-scenario checks. No separate benchmark, migration, audio/key/clipboard capture, monitor fallback or new runtime is required. The inspected WGC route is monitor-oriented, not Spindle's target-window/privacy contract. Source inspection establishes design lessons, not measured superiority or Spindle native acceptance. Keep any future source-adoption/licensing review separate from this learning task; no third-party source incorporation is proposed here.

### Context and screenshots

- Default prefers permitted native/DOM text; structured extractors exclude password/form-entry/editable/hidden content. A title or toolbar label is not complete body text. Unsupported apps/fields remain unavailable. Explicitly consented, provenance-verified native window pixels/OCR may include visible edited content and sensitive fields; read-only/edit-state/layout is not a capture prerequisite. Screenshots do not mask fields: source scope/exclusions are the boundary. Browser detail/pixel restrictions are unchanged, including private/unknown-source denial and no native fallback.
- OCR has explicit pixel permission. Temporary frames are memory-only where possible, bounded and destroyed after local extraction; no retained image, thumbnail, debug dump or image-bearing cache in Default.
- Rich reuses the visit and independently admits a screenshot. Prefer a verified target-window surface; do not silently capture a whole monitor with unrelated/private windows. Validate target/focus before and after asynchronous capture. Unknown association is a dropped result with a content-free reason.
- Separate capture, processing, local retention and remote-egress scopes. Capture does not grant retention. No remote egress in this milestone.
- Retained text and images require an explicit expiry and inspect/delete path. Implement encrypted context storage and OS-protected key handling before enabling retained content; keep content out of plaintext SQLite/WAL/logs. Baseline metadata is user-private local storage, not claimed encrypted without implementation.
- Raw expiry versus explicit deletion are distinct: explicit deletion invalidates linked context, derived results, pending jobs and application-controlled copies. Crash/orphan cleanup must be testable. No claim of forensic SSD erasure.

### Native versus browser responsibilities

OS permission is not a universal browser instrumentation API. Native Accessibility/automation may expose an address bar, title and some page text, but availability varies across browser/version and does not reliably establish document identity, private state, SPA transitions or player behavior. Native app recording can operate without the extension; missing browser capability remains explicit. Never make an extension a prerequisite for unrelated native capture.

The companion is the selected path for structured, privacy-checked browser context on supported profiles and later content-aware browser controls. It is not a second native application or a replacement for OS capture. Browser capability needs browser-specific proof; it is not inferred from Screen Recording or Accessibility grants.

### Browser boundary

Initial target: one explicitly supported Chromium browser family, individually enrolled profiles, and an authenticated local Native Messaging path. Document exact supported versions in the foundation decision. No open ingest port, broad native command API or profile auto-adoption. Unknown/private browsing detail is denied. Extension loss must not turn browser time into confirmed ordinary activity. Browser screenshot capability may be manual/limited; report the actual trigger/coverage rather than claiming every visit has a frame.

Browser resource identity must not depend on retaining a raw URL query. For example, YouTube's watch-page video ID is commonly in `v=`, while other routes encode it in the path. Under a separately named content-identity scope, extract and validate an allowlisted typed `video_id` before discarding the query; strip all unrelated parameters. Do not broadly permit queries or treat an opaque video ID as a content classification. The identity remains browsing data with consent, retention and deletion rules; it is not automatically approved for remote inference.

### Future content-aware gate (outside the capture milestone)

An always-gated YouTube policy is distinct from a temporary whole-domain unlock. The proposed sequence is gate → resolve current content identity → evaluate permitted metadata/classification → apply the user's eligibility/allowance policy → grant a bounded permission for that video. Unknown, failed, stale or missing classifications stay gated with review/recovery; a classifier result alone never grants an entire domain or mints credit.

A classification worker may use Jev only after a separate input-contract/privacy/quality review. Domain-only classification cannot distinguish videos. Do not send a personal raw URL or load a fully playing page merely to obtain metadata: prove a permitted pre-play metadata path or a non-playing gate, with explicit remote-field consent if needed. Treat page text as untrusted input, not instructions. Video identity, model/policy revision and expiry bind cache/allow decisions; stale results from a prior video cannot release the current one.

Enforcement belongs in the enrolled browser profile, with the native app owning local policy/accounting. Request rules can block/redirect matching navigation, but do not implement arbitrary AI checks or reliably bind YouTube's shared media requests to a watch-page allowlist. Content/player controls must also handle SPA routes, direct links, Shorts, embeds, live videos, autoplay/next, existing tabs, multiple tabs, expiry and extension/host failure. A content-script overlay or pause alone is not proof of zero pre-gate playback; measure races and state actual guarantees before promising strict gating. Never imply DNS/hosts filtering can provide per-video exceptions, intercept HTTPS, or cover unenrolled browsers/native YouTube apps by default.

### Host lifecycle and failure

Run as the current OS user, without elevation or cross-user capture by default. Recording and optional login startup require explicit consent. A pause/revoke fence persists through crashes and restart; uninstall removes registrations and explains retained/deleted data. Backpressure drops optional work before it harms timing, with bounded queues and visible partial coverage. No collector starts merely from opening a dashboard or signing in.
